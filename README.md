## The Crucible Concept

Crucible reimagines how software is built by separating app development into
two layers:

* Developers contribute the **operational logic** that makes systems function.
These contributions - called _resources_ — define services and how frontends
interact with them. This is the engine that powers Crucible’s ecosystem.

* Product professionals handle the **composition stage**. They choose which
backend services to integrate. Each service includes a set of frontend widgets
that become available once the product professional selects that service. They
can then drag and drop these widgets onto a canvas to compose user experiences
— the logic is already built-in.

When a product professional pays to use a service, **Crucible shares part of
that revenue** with the developer whose logic enables it. Developers build.
Product professionals compose. Both benefit.

## The Tiered Model

Crucible features a **tiered model** to reward developer participation. As
developers contribute, they earn **points** that raise their tier and unlock
new rewards.

Each tier increases their **revenue share**, up to **75%** at the highest tier.
The more a developer contributes to Crucible’s ecosystem, the more they earn
from the services that depend on their work.

### 2. Scaffold a Service

A **service** is a Crucible resource that runs on the backend. It processes
requests and exposes functionality to other resources through APIs.

To scaffold a service, open a terminal and type:

```sh
crux init
```

This creates a simple service on the working directory. See other scaffolding
options with `crux init --help`.

Once the service is created, refer to the included `README` file for additional
instructions. It explains how to test, build, package, and distribute your service.
